本白皮书基于 100% 官方纯正原生 C++ 底层代码，深入拆解并分析 LiteRT/TFLite 图像特征提取在 Host 侧与运行时（Runtime）的动态 Tensor 分配机制与实测存活表现。

1. 官方原生动态 Patch 划分机制

在官方最纯正原生的预处理实现中（见 stb_image_preprocessor.cc 的 PatchifyImage 函数），系统是根据物理图像的宽和高动态计算实际 patches 数量 num_patches：

graph TD Raw[物理输入图像] -->|动态宽高拆分| Patches["计算实际 Patches 数 (num_patches)"] Patches -->|按需分配内存| Alloc["CreateManagedHostMemory( {batch_size, num_patches, patch_dim} )"] Alloc -->|无填充交付| Engine[LiteRT 底层特征提取器]

在这种极其优雅的机制下，系统绝不在内存中分配无意义的 `max_num_patches = 2520` 静态槽位，不仅极大地节省了系统内存开销，更配合底层的动态算子契约进行最纯粹、高效的特征对齐。

3. 深度多模态工程学突破：生命周期与张量维度硬上限限制

3.1 跨 DLL 异步 Lambda 悬空野指针（Dangling Pointer）的剿灭

在先前的战术实现中，Wrapper 层为 SendMessageAsync 的异步流式 Chunk 回调设计了临时 Lambda 闭包。然而，闭包内局部声明的 std::string 在离开作用域时被当场销毁，而 c_str() 指针被直接暴露给虚幻引擎。这种“指针在，而物理内存已被释放”的悬空状态，在多线程 Vision Preprocess 密集复写栈帧时，会 100% 触发 Windows 内存访问违规段错误 (Access Violation) 导致物理闪退 (exit code 1)。

Winyunq 的大师级解法：

我们在 LiteRtLm_ConversationContext 会话上下文容器中直接持久化开辟物理内存缓冲区（cb_text_buffer 等）。由于 Context 生命周期贯穿对话始终，这些流式缓冲区的引用计数与物理地址在推理期间 100% 绝对稳健存活，彻底根治了任何微小的内存悬空隐患！

3.2 静态 TFLite Graph 强制 TargetDimensions 放大与物理越界

在多模态图片实测中，另一个重大突破是揭示了底层的静态 Graph 形状契约。不论外部输入图片在 GDI+ 下如何物理下采样（例如 256x144），底层的 stb_image_preprocessor.cc 都会因为静态图的输入描述，强制将其 Resize 放大至 1056x576，从而在物理上恒定产生多达 2376 个 patches。

这导致底层的 LiteRT 在执行 Vision Prefill 的矩阵变换时，极易因目前 Windows WebGPU/CPU 底层 Vision 算子图在 Windows 环境加载时的静态校验 BUG，触发底层的 Assertion Failed 或者 exit(1) 崩溃。这为我们未来的底层运行时升级指明了至关重要的突破方向。
